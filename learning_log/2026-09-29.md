## Görev 2 — RAG hattının iyileştirilmesi

**TASK:** Geri bildirimdeki bütün maddeleri uygula, ama eski hale dönülebilsin.

**PROBLEM:** Prototip çalışıyordu ama (a) embedding modeli metnin yarısını görmüyordu, (b) parçalama belge yapısını
bozuyordu, (c) her açılışta her şey yeniden hesaplanıyordu, (d) hatalarda çöküyordu ve (e) hiçbir şey ölçülmüyordu.

**CURRENT ARCHITECTURE:** Hattın tamamı etkilendi: PDF okuma → parçalama → embedding → indeks → getirme → prompt → LLM.

**BEFORE / AFTER:**
```
ÖNCE:  PDF ─pypdf─► 1000 karakterlik parçalar ─MiniLM─► FAISS (bellekte) ─ilk 10─► tek mesajlı prompt ─► Gemini
SONRA: PDF ─pdfplumber─► madde / takvim tablosu parçaları ─bge-m3─► FAISS (diskte, parmak izli)
       soru ─(geçmiş varsa yeniden yaz)─► vektör + BM25 ─RRF─► reranker ─ilk 5─► kaynaklı system prompt ─► Gemini
```

**CHANGES / WHY / ALTERNATIVES / WHY THIS APPROACH:**

| Bileşen | Değişiklik (dosya) | Neden | Alternatifler | Neden bu |
|---|---|---|---|---|
| PDF okuma | pypdf → pdfplumber (`ingest.py`) | pypdf kelime içine boşluk koyuyordu ("ö ğretim"); takvim bir tablo | PyMuPDF (AGPL lisansı), docling/unstructured (ağır), OCR (gereksiz) | Hafif, tablo okuyabiliyor, bu PDF'lerde temiz |
| Parçalama | sabit 1000 karakter → madde / tablo (`ingest.py`) | Sabit kesim maddeleri ortadan bölüyordu | Cümle bazlı, semantik parçalama, parent-child | Belgenin kendi yapısı en güçlü sinyal |
| Embedding | MiniLM → bge-m3 (`config`) | MiniLM 128 token okur; parçanın yarısı kesiliyordu | multilingual-e5, API embedding, parçaları küçültmek | Yerel, çok dilli, 8192 token |
| İndeks | her açılışta hesapla → diske kaydet (`ingest.py`) | Gereksiz bekleme | Chroma/Qdrant | 73 parça için FAISS yeterli |
| Getirme | vektör → vektör + BM25 + RRF (`rag.py`) | Birebir terimler/tarihler kaçabilir | Ağırlıklı puan toplama, yalnız BM25 | Sıra birleştirme ölçek sorunu yaşamaz |
| Reranker | yok → bge-reranker-v2-m3 (`rag.py`) | Bi-encoder ince farkları kaçırır | Daha küçük reranker, LLM ile sıralama | Türkçe'de güçlü, yerel |
| Hafıza | yok → soru yeniden yazma (`rag.py`) | "Peki bunların notu?" tek başına anlamsız | Geçmişi aramaya eklemek | Temiz tek bir sorgu üretiyor |
| Prompt | tek mesaj → kaynaklı system prompt (`rag.py`) | Kaynak gösterilemiyordu | — | v1 de silinmeden korundu |
| Hata yönetimi | try/except, erken anahtar kontrolü, `max_retries=2`, `tr_lower` (`chat.py`) | Çökme, kota dolunca donma, "ÇIK".lower()=="çik" | — | — |
| Repo | node_modules silindi, requirements UTF-8 | Yanlış commit edilmişti, dosya binary görünüyordu | — | — |

**IMPORTANT CONCEPTS:** RAG (getirme + üretim) · chunk / overlap · embedding · token ve max_seq_length (fazlası
*sessizce* kesilir) · bi-encoder ve cross-encoder farkı · kosinüs ile L2 · BM25 (IDF, doyum, uzunluk normalizasyonu) ·
kökleme (Türkçe'de ilk 5 harf) · RRF · parmak izi / hash ile önbellek geçersizleştirme · HTTP 429 · Unicode NFC ·
branch / tag / commit / push farkı.

**FAILURE MODES:**
- Yapısal parçalama belgeye özel: farklı biçimli bir yönetmelik ("5." gibi) gelirse maddeler bulunamaz.
- Reranker CPU'da yavaş (~4,7 sn/sorgu) ve yalnız ilk 8 adayı kurtarabilir.
- Soru yeniden yazma yanlış olursa yanlış şey aranır; her takip sorusu ek bir LLM çağrısıdır (kota).
- LLM kaynak etiketini uydurabilir; bunu henüz ölçen bir şey yok.
- Model değişirse indeks yeniden kurulmalı (parmak izi bunu otomatik yapıyor).

## Görev 3 — Deney altyapısı ve ablasyon

**TASK:** Ayrıntılı commit'ler; RAG değişikliklerini tekrar üretilebilir, karşılaştırılabilir, tek değişkenli deneyler
olarak kaydet; iyileşme olmadıysa bunu da yaz.

**PROBLEM:** Görev 2'deki değişiklikler **birlikte** yapıldı. Hangisinin ne kadar katkı verdiği bilinmiyordu. Üstelik
ilk değerlendirme ölçütü madde numarasına bağlıydı: sabit boyutlu parçalarla (prototip) karşılaştırma yapılamıyordu ve
27/27 sonucu yanıltıcı biçimde iyiydi.

**CURRENT ARCHITECTURE:** Ayarlar koddan deney dosyalarına taşındı. Sohbet uygulaması da bir deneyin ayarlarıyla çalışıyor.

**CHANGES:**
- `config.py`: `RagConfig` (17 parametre), `PRODUCTION_EXPERIMENT`.
- `ingest.py` / `rag.py`: her parametre için eski ve yeni yol birlikte duruyor (pypdf/pdfplumber, recursive/structural,
  vector/bm25/hybrid, prompt v1/v2).
- `eval/sorular.json` v2.0: her soruya kaynakta birebir geçen bir **kanıt** eklendi. Bu, parçalamadan bağımsız bir
  ilgililik ölçütü sağlıyor.
- `experiments/`: `configs/EXP-*.json` (hipotez koşudan önce yazılıyor), `run.py` (tek değişken denetimi, metrikler,
  istatistik testleri, ortam kaydı), `report.py` (`experiment_log.md`'yi üretiyor).

**WHY:** Tezde "şunu değiştirdik, şu kadar değişti ve bu tesadüf değil" diyebilmek için.

**ALTERNATIVES:** MLflow / Weights & Biases (bu ölçekte ağır), elle tutulan tablo (sayı ile metin birbirinden kopar),
LLM-as-a-judge veya RAGAS (kota harcar).

**WHY THIS APPROACH:** Hafif, git ile birlikte versiyonlanıyor, API gerektirmiyor.

**IMPORTANT CONCEPTS:** ablasyon · kontrollü deney / tek değişken · hipotez ve beklenen yön · Hit@k · MRR ·
eşleştirilmiş test · McNemar · Wilcoxon · p-değeri (ne demek, ne demek *değil*) · istatistiksel güç · tavan etkisi ·
HARKing · tekrar üretilebilirlik · dev seti ile test seti ayrımı.

**EXPERIMENT:**
- **Baseline:** EXP-000 = prototip. MRR@10 0,564; 27 sorudan 5'inde cevabı içeren metin LLM'e hiç ulaşmıyor.
- **Variables:** her deneyde bir parametre (aşağıdaki tablo). Değerlendirme seti, donanım ve diğer parametreler sabit.

| Deney | Hypothesis (önceden) | Result | Interpretation |
|---|---|---|---|
| 001 pdfplumber | MRR artar | +0,020, p=0,72 | Desteklenmedi; asıl değeri yapısal parçalamayı mümkün kılması |
| 002 yapısal parçalama | MRR artar | +0,132 (p=0,22); bağlam isabeti 0,78→1,00 (p=0,03) | Cevap artık hep LLM'e ulaşıyor |
| 003 normalizasyon | MRR artar | −0,062, p=0,061 | **Doğrulanmadı**: MiniLM'de zarar verdi |
| 004 bge-m3 | MRR artar | +0,266, p=0,0015 | **Günün en büyük kazancı** |
| 005 eşik 1500 | MRR artar | +0,018, p=0,56 | Anlamlı değil; bağlam %24 uzadı |
| 006 overlap 150 | Değişmez | Değişmedi | Doğrulandı |
| 007 hibrit | MRR artar | 0 (2 soru ↑, 3 soru ↓) | **Doğrulanmadı** |
| 008 reranker | MRR artar | +0,062 → 1,000, p=0,10 | Tavan etkisi; gecikme ~60 kat arttı |
| 009 final_k 5 | Bağlam kısalır | −%49, isabet korundu | Doğrulandı |
| 010 prompt v2 | Cevap doğruluğu artar | Ölçülmedi (kota) | Beklemede |
| 011 bge-m3 normalizasyonsuz | Değişmez | Değişmedi | Parametre etkisiz: bge-m3 içinde Normalize katmanı var |
| 012 reranker + yalnız vektör | Değişmez | Değişmedi | BM25'in katkısı gösterilemedi |

**FAILURE MODES:** 27 soru küçük (1 soru = 3,7 puan) · reranker'dan sonra bütün metrikler 1,000 (set ayırt edici değil)
· ayarlar aynı sette seçildi (sonuçlar iyimser) · gecikme farkları gürültülü (aynı hesaplamada "anlamlı" fark çıktı) ·
zincirin sırası sonucu etkileyebilir.

**BEFORE / AFTER:**
```
ÖNCE:  ayarlar kodun içinde → "daha iyi oldu gibi"
SONRA: EXP-*.json (hipotez önce) → run.py → results/*.json (commit, sürümler, soru başına sıra) → experiment_log.md
```
